# Godot 移植计划（JS → Godot 4.4 / GDScript）

> 目标：把《开拓者：殖民地》从 JS + Canvas 完整搬到 Godot，**同一种子生成同一张地图**。
> JS 版冻结但保持可运行（绿色版仍可发布），所有新功能只在 `godot/` 里做。

## 怎么跑

```bash
node tools/export-godot-data.mjs     # src/data/*.js  →  godot/data/*.json（改数值后要重跑）
node tools/godot-verify.mjs          # 生成黄金值 + 跑 Godot headless 测试 + 断言

# 直接开工程（编辑器）
tools/godot-dl/exe/Godot_v4.4.1-stable_win64.exe --path godot
# 直接跑游戏
tools/godot-dl/exe/Godot_v4.4.1-stable_win64.exe --path godot --quit-after 30   # headless 冒烟
```

Godot 本体放在 `tools/godot-dl/exe/`（已下载 4.4.1，`godot-verify` 会自动找）。

## 验收方式：黄金对比（跨语言逐位一致）

移植最大的风险不是「写不出来」，而是**悄悄写错一位**：世界生成、掉落、实验科技
全建立在 RNG 与噪声上，一位不一样就整张地图不同、老存档对不上。
所以第一阶段就把这个风险关掉：

```
tools/godot-golden.mjs   用 JS 实现算出一批数值 → godot/tests/golden.json
godot/tests/run_tests.gd 用 GDScript 实现算同一批 → 逐位比对（1e-9 相对误差）
```

当前：**228 条断言全绿**。

### 已经踩到的三个「逐位一致」陷阱（都靠黄金对比抓出来）

1. **ToInt32 截断**。JS 的 `t ^= t + Math.imul(...)` 里，`+` 会先算出超过 32 位的结果，
   再由 `^` 触发 ToInt32。GDScript 的 int 是 64 位，不截断就把高位卷进 XOR ——
   数值只差 6e-5，看着「差不多」，实际整个世界都不同。必须 `& 0xFFFFFFFF`。
2. **JS 的浮点乘法本来就有舍入**。`hash2` 里 `seed * 1442695041` 能到 6.2e18，
   超过 float64 的整数精度（2^53）。用 int64 精确算**反而对不上** ——
   必须照 JS 那样在浮点里算完再取模。（复刻精度误差是这里唯一正确的做法。）
3. **稳定排序**。JS 的 `Array.sort` 保证稳定，GDScript 的 `sort_custom` 不稳定。
   降落点候选里大量元素 `danger` 完全相同，不稳定排序让「取前 4 个」完全不同 ——
   表现为降落点坐标全错、基地被铺到别处。

### 还有一类「测试脚手架自己造成的假失败」

比上面三个更阴：**两边数据的历史不同**，导致哈希对不上。
流场的 `dist` 数组跨代复用（靠 `stamp` 标记有效格），JS 那边旧值会留着；
GDScript 侧每次新建对象、初值是 INF —— 于是「整张数组的哈希」必然不同，
但这**不是**移植错误。修法是两边都只统计**本代有效**的格子。
教训：跨语言比对时，要保证比的是**语义状态**，而不是「对象里碰巧残留的字节」。

## 阶段 4 的做法与发现

### 渲染：图集 + 逐格绘制（不再需要区块缓存）

JS 版是「每个 16×16 区块烘一张 canvas 再整张贴上去」，因为 canvas 逐格画矢量太慢。
Godot 这边反过来：**所有地块共用一张程序化图集**，Godot 会把同材质的
`draw_texture_rect_region` 合批，于是逐格画既简单又快（实测 792 个可见格 + 51 条崖边
在 1280×720 下 **FPS 247**）。

- `tile_atlas.gd`：把「19 种地块 × 5 档明暗」烘成一张图集。
  JS 里 `shade(color, (v-0.5)*0.10)` 是连续变化，这里量化成 5 档（±0.05 以内人眼无感）。
- `terrain_layer.gd`：逐格贴图 + 崖边描边（规则与 JS 的 `drawSolidEdge` 完全一致，
  用 4 位掩码哈希做了黄金对比）。
- 顺带消掉了一个坑：JS 那个「区块缓存键必须带 world.uid」的问题在 Godot 版
  **根本不存在**（没有区块缓存）。但 `GdWorld.uid` 仍然保留了 —— 小地图底图要用它
  区分「这是哪张世界」，进副本时才不会继续画地表的底图。

### 截图验证：让游戏自己截图

第一次想用系统 API 抓窗口，结果**抓到了桌面壁纸**（Godot 是 GPU 渲染，窗口没在最前
时拿到的是别的东西）。改成游戏自己截图：

```bash
node tools/godot-shot.mjs --out tools/shots/godot-game.png --seed frontier-golden-a --frames 120 --move 1,0
```

原理是 `-- --shot=<路径> --frames=N` → 跑 N 帧后 `get_viewport().get_texture().get_image()`
存 PNG 再退出。可无人值守，也顺带把 FPS 打出来。

### 发现一个 JS 版的老 bug（暂不改，先记下来）

基地地面被**巢穴焦土**啃成了棋盘格：

```
基地中心 (59,178) 周围（C=混凝土 x=焦土）
xxxxx.xx..CCCxCCCCC..."""....
""xx"~~.xCxxC~CxxCCC...""....
```

`基地 17x17 内统计: {"1":84,"2":14,"4":12,"8":2,"13":89,"14":88}`
—— **89 格混凝土 vs 88 格焦土**，正好一半。

原因：`generate()` 里 `_applyScars()` 排在 `_carveStarterZone()` **之后**，
而巢穴焦土半径是 `tier*3+6` 格（5 级巢就是 21 格），比降落点的「10 格内不许有巢穴」
大得多，于是焦土直接糊到基地上。

**这次不改**：JS 版已冻结，改了就对不上黄金值了（tiles 哈希会变）。
等 JS 版解冻时两个版本一起修，修法是 `_applyScars` 里跳过
`dist(tile, baseSite) < 16` 的格子。当前 Godot 版**忠实复刻**了这个行为。


## 阶段 5：属性引擎与武器数值（这一层的坑）

属性引擎（`stats.gd`）是整个成长系统的地基：角色被动、主科技树、实验科技、
装备词缀、基因、临时 buff 全都产出同一种「修正」，由它算成 123 个数值键 +
机制对象。移植时要复刻三条规则：

1. **数值键加法叠加**；
2. **对象键（机制）取「最强」的一份** —— `strongerMechanic` 按
   `mult*100 + dmg*10 + dmgMult*100 + amount + dps*5 + chains*20 + radius*0.2` 打分
   （黄金对比里特意放了两份 `towerExplode`，验证 radius 90 的那份胜出）；
3. **临时 buff 的同名 id 会替换旧的**，过期自动消失。

武器层（`weapon_math.gd`）复刻四条硬上限与弹药整数化：射程/伤害 +300% 封顶、
射速 +200% 封顶、弹道最多 3 条、换弹 `max(0.5, round(基础×品质×100)/100)`，
弹药永远是整数（零头记在 `ammo_frac`）。

### GDScript 特有的坑：`Object.get()` 不能覆盖

JS 里 `StatSet.get(key)` 是核心 API，但 GDScript 的 `Object` 已经有 `get(name)` ——
同名会被引擎拒绝（而且警告当错误）。所以移植版叫 **`stat(key)`**，
同类要小心的方法名还有 `set` / `call` / `free`。

### 两个自己踩的坑

1. **忘了调用 `update()`**：弹丸系统写好了也 `setup()` 了，但 `_process` 里只推了敌人
   没推弹丸 —— 表现是「子弹全堆在枪口、命中数永远 0」，而且**不报任何错**。
2. **GDScript 没有 `bool()` 构造器**：JS 里到处 `!!v`，照搬写 `bool(v)` 会直接报错；
   现在统一用 `GdMath.truthy(v)`。

## 阶段 7：防御塔与建造

玩家最在意的那条规则（原话「我给防御塔基座加条件让他可以取消掉防御塔的间隔」）
在这一阶段落地，而且**用两种方式验证**：

1. **纯逻辑黄金对比**：169 个候选点逐个问 `find_placement` → 能不能放、落到哪一格、
   是不是在基座上，与 JS 完全一致；再加三个场景——
   - 基座上放塔 → 允许（`onPlatform = 1`）
   - 空地上贴着已有的塔放 → 被挤到邻格（间隔规则）
   - **相邻两块基座上各放一座塔 → 允许，两塔只差一格**（这就是「免间隔」）
   - 普通建筑旁放塔 → 被挤开
2. **端到端断言**（Godot 侧真实调用 `place_structure` / `place_tower`）：
   铺基座 → 塔落在基座上 → 相邻基座再来一座 → 两塔间距 < 44px；
   对照组：空地上两座塔间距 ≥ 44px。

数值侧：11 座塔 × 3 档科技（白板/中期/顶满）逐值比对 hp/射程/伤害/3 级伤害/间隔/
上限/造价。

### 这一阶段抓到的两个真 bug

1. **建筑把自己的格子标成了不可通行**。`place_structure` 无条件
   `world.set_blocked(..., true)`，而 JS 里只有 `blocks: true` 的建筑（墙）才占位。
   后果：`find_placement` 第一步 `is_blocked_px` 就跳过基座那一格 →
   **塔永远放不到基座上**，正是玩家抱怨的「基座太鸡肋」。
   注意：**黄金对比抓不到这类集成错误**（它只比 `find_placement` 的纯逻辑），
   所以补了上面那条端到端断言。实测从「塔 4 座（基座上 0）」变成「塔 4 座（基座上 4）」。
2. **JSON 的 `null` 与 JS 的 `||` 语义**。导出时 JS 的 `undefined` 变成 `null`，
   而 `Dictionary.get(key, default)` 只在**键不存在**时兜底 —— 键在、值是 null 时
   返回 null，`float(null)` = 0；更隐蔽的是 JS 写的是 `(def.dmg || 10)`，
   **支援塔的 `dmg` 本来就是 0**，JS 会兜到 10，而「只在缺失时兜底」的实现算出 0。
   现在数据读取统一走 `DataLoader.num_or() / num() / bool_of()`。

实机（截图 `tools/shots/godot-towers.png`）：一排 4 座塔**只隔一格**（每座底座亮一圈绿光
表示「坐在基座上」），HUD 显示 `塔 4（基座上 4）· 建筑 4`，塔已经打死了 4 只怪。

### 端到端 vs 纯逻辑：为什么两种测试都要有

阶段 7 抓到的那个 bug（建筑把自己的格子标成不可通行 → 塔放不到基座上）
**黄金对比完全看不到** —— 它比的是 `find_placement` 这个纯函数的输入输出，
而 bug 出在「谁把哪一格标成 blocked」这个集成层。
所以每搬一个系统，除了数值对比，还要在 Godot 侧写一条**真实调用链**的断言
（铺基座 → 放塔 → 检查 onPlatform）。

## 阶段 8：波次导演与吸引阵列（顺带挖出 JS 版一个必崩的 bug）

### `director.nextInterval()` 每波必崩

移植时要把 `nextInterval()` 翻译成 GDScript，我在 JS 里找它的实现，发现：

```js
nextInterval() {
  // 这里用了 run 和 base，但整个方法没声明它们
  if (run.isTowerDefense) { ... }
  const nests = run.world.nests.filter(...)...
  return clamp(base * (0.6 + nestFactor * 0.55), ...);
}
```

文件里其他**每一个**方法开头都有 `const run = this.run;`，唯独这个漏了。
后果：一波怪结束 → 26 秒善后期 → 计时归零时抛 `ReferenceError: run is not defined`，
而且**每波必然复现**。前面藏了这么久，是因为一波要 150 秒以上，
短时间试玩根本碰不到 —— 我之前的探针也都没跑够一整波。

- 复现脚本：`tools/probe-nextinterval.mjs`（改波次状态到善后期末尾，调 `updateWave`）
- 修复：补上 `const run = this.run;` 与 `const base = BEACON.waveIntervalBase;`
  （下文 `base * (0.6 + …)` 显然是「间隔基数」，也就是 `waveIntervalBase` = 150）
- 回归防线：`smoke.mjs` 新增 4 条断言（两种模式各 2 条），推着善后期走完整分支

> **这极可能就是玩家之前报的「现在出现的报错」** —— 那个我一直没能复现的错误。

### 波次系统的黄金对比

| 项 | 验证方式 |
|---|---|
| 组成 | 3 组（1/4/2 级吸引阵列）**逐只**比对怪种与来源巢穴 —— 顺序也必须一致，等于验证随机数消耗顺序 |
| 预算 | Lv1 → 15 只 1 个巢；Lv4 → 88 只 7 个巢（强度把范围外的巢也「部分牵引」进来） |
| 燃料 | 每波固定扣 6 |
| 间隔 | 172.5 秒（巢穴全在 → `base × 1.15`，被上限 210 夹住） |
| **刷怪点四档规则** | 5 种场景：巢在屏幕里（**离巢 102px，从洞里出来**）／巢很远（**离巢 167px**）／巢在屏幕边（**离巢 204px、离相机恰好 1004px = standoff**）／斜向边缘（同样推到 1004）／没有巢（随机方向推到 1004） |

截图 `tools/shots/godot-wave.png`：日志打出「第 1 波：21 只，来自 3 个巢穴」，
画面里怪从巢的方向走进来、4 座基座塔在开火。
### 已知问题：世界生成比 JS 慢 25 倍

实测（`godot/tests/perf_worldgen.gd`）：

| 实现 | 一次世界生成 | 备注 |
|---|---|---|
| JS（V8 JIT） | **~200 ms** | 现在 JS 版是开局瞬间完成 |
| GDScript（4.4.1，无 JIT） | **~4.9 s** | 每个地块要算 5 层 fbm + ridged + warped，9.2 万格 |

这不是「写错了」，而是 GDScript 解释执行的固有代价。三条可选对策（阶段 4 之前定）：

1. **结果缓存**：生成一次后把 tiles/biomes/variant 写进 `user://world_<seed>.bin`，
   之后秒开（存档本来也要记录种子）；
2. **线程池 + 进度条**：`WorkerThreadPool` 里分块生成，主线程显示进度；
3. **关键热路径换语言**：只把噪声/地形循环用 GDExtension(C++) 或 C# 写
   —— 但那样就不再是「纯 GDScript」，需要单独权衡。（注意：换成 FastNoiseLite
   这类内置噪声会**丢掉与 JS 的逐位一致**，现有存档的地图就对不上了。）

建议 1+2 组合：首次生成给进度条（约 5 秒可接受），之后从缓存秒开。

## 阶段 9：虫巢副本

挖掘结果与 JS 逐位一致（4 个等级各比一次）：

| 项 | 内容 |
|---|---|
| tiles 哈希 | T1/T3/T6/T10 各一次 |
| 地块构成 | 巢壁 9 万+ / 巢道 705~1519 / 巢核 40 / **其它 0**（没有地表残留） |
| 清理 | props / 巢穴 / 遗迹全清空、`no_props` 置位（就是「副本里怎么和外面一个风格」那条的修法） |
| 关键坐标 | 入口 (92,152)、玩家出生 (100,152)、Boss 房随等级 159→199 |
| Boss 房 | 15×15 / 19×19 / 23×23（等级越高越大）+ **四角柱子** 4/4 |
| 主通道 | 从入口到 Boss 房每 5 格取样，必须全是可走的巢道/巢核 |

**架构上与 JS 版同构**：副本是**另一个 World 对象**（`DungeonFlow`），
地表那份原封不动留着，出来时切回去 —— 所以地表的塔、城镇、巢穴进度不会被污染，
也不需要「出副本重新生成地表」那 5 秒。

实机（截图 `tools/shots/godot-dungeon.png`）：暗色巢壁 + 暗红巢道、左端入口大厅
（巢核地面）、右侧主通道、上方一条支路通向侧室，小地图画出鱼骨形状。

### 这一步踩的坑：`_draw()` 不会自己重画

进副本后画面变成一整片**清屏色**（HUD 还显示着 792 个可见格，其实那是旧数字）。
原因：CanvasItem 的 `_draw` 只在被要求时执行，而地形层只在 `setup()` 里画过一次。
玩家一传送，旧画面就跑到视野外，新画面从来没画过。地表上没暴露，
是因为开局画过的那一块一直在视野里。

修法：地形层加 `_process` 每帧 `queue_redraw()`（相机跟随的地图本来就该这样），
换世界时再让相机 `reset_smoothing()` 直接怼到新位置。

### 这一阶段抓到的两个「我自己的」移植 bug

1. **吸引阵列等级差一位**。JS 里 `beacon.level` 从 **0** 起，半径是
   `900 + level×300`（0 级 → 900）；我写成了 `900 + (level-1)×300` 且默认 1 级。
   ⚠️ 更值得记的是：**这个错误一开始没被测试抓到** —— 因为我在黄金对比的
   JS 脚手架里**自己重新推导了一遍公式**，把同样的错值写进了期望值，

### 又一个 JSON ↔ GDScript 的静默陷阱：`Array.has(1)` 匹配不到 `1.0`

道具池一开始**全是兜底的「飞船残骸」**（353 个里 183 个残骸 + 152 个金属堆，
本该是灌木/矿脉/晶簇）。原因：

```gdscript
if not biomes.has(biome): continue        # biomes = [1.0, 0.0, 5.0]，biome = 1 (int)
```

**JSON 里的数字一律是 float**，而 GDScript 的 `Array.has()` 按类型严格比较 ——
`has(1)` 在 `[1.0, …]` 上返回 false，于是**所有带 biome 限制的道具全被跳过**，
池子里只剩 `biome: null` 的那几个（残骸/方尖碑/补给箱），再被「一半变金属堆」
的规则一变，就成了满地的残骸。

教训与之前的 `null` 陷阱同源：**从 JSON 读进来的数字/空值，都要当成异构类型处理**。
现在统一 `int(b) == biome` 逐项比。

## 阶段 12：存档 / 读档（设置与 Steam 见末尾说明）

JS 版在这里踩过一个**静默**大坑：`serializeBases()` 忘了存核心舱的 `r`（交互半径），
读档后 `b.r` 是 `undefined`，判定 `dist < b.r + 40` 变成 `NaN < 136` → **永远 false**
→「按 E 重建核心舱」完全没反应，而且不报任何错。玩家报的就是这个。

所以移植版立了三条规矩，并用断言把它们钉住：

1. **每个字段都有显式默认值** —— 缺字段走默认，绝不许变成 NaN 再静默生效；
2. 存档带 `version`，旧档按兼容模式读；
3. **往返（存→读→再存）逐字段一致**，并且专门盯着那三个「历史坑字段」。

| 验证项 | 内容 |
|---|---|
| 坑字段存在性 | `bases.r` / `beacon.x` / `beacon.y` / `towers.onPlatform` 必须在存档里**真实存在** |
| 往返逐字段 | 玩家坐标/hp/死亡数/弹药/武器品质、资源、科技集合、实验等级、基地(r/buildRadius)、塔(类型/等级/是否在基座上)、建筑、载具(油/挂架)、吸引阵列(位置/等级/燃料)、波次(编号/状态/计时)、统计（击杀/建塔/波次/采集） |
| 残缺存档 | 只给 `{version, player:{x}}` 也必须能读，且 hp/hpMax/base.r **不是 NaN、不是 0** |

实机（`--saveload=1`）：

```
[godot] 存档往返：成功 → 读回 hp 88 · fiber 33 · wave 7 · 科技 2 项 · base.r 96
[godot] 存档往返比对：hp 122→88 · fiber 33.0→33 · 槽位 slot1
```

存档写在 `user://saves/<槽位>.json`；`SaveGame.save()` 写完会**立刻读回来校验一次**
（写坏了要当场知道，而不是等玩家读档时才发现）。

### 又一次「脚手架不能自己写实现」的教训

我第一次写人口增长的黄金值时，**手写复刻**了 `updatePopulation` 的循环 —— 结果漏了
真实实现里断粮分支的 `return`，于是黄金值记录了一个**游戏里根本不会发生**的行为
（食物为 0 时人口还一路涨到上限）。测试当然全红。

改成**直接驱动真实的 `TownSystem.updatePopulation`**（并把 `popCap` 也改成读真实的 getter）
之后，GDScript 侧立刻暴露出两个真实差异：`popCap` 少算了 4 点基础容量、`growthTimer`
初值应该是 6 而不是 0。两个都修好了。

> 这条规矩现在写死在流程里：**黄金值的脚手架必须调用实现本身，不许凭记忆重写**。
> 这是第二次踩（第一次是吸引阵列半径公式），两次都是「测试确认了自己的错误」。

加了设置面板之后，截图从 **1280×720 变成 2558×1438**。原因不是缩放逻辑本身，而是
`apply()` 里那句「确保窗口模式正确」：在 **200% 显示缩放**的 Windows 上，
一次多余的 `DisplayServer.window_set_mode(WINDOWED)` 会把窗口按**物理像素**重建一遍。

修法：`apply(tree, apply_window := false)` —— **启动时绝不碰窗口模式**，
只有玩家真的拨动「全屏」开关时才传 `true`。另外三目运算符**不能跨行**
（GDScript 把换行当语句结束），那处也改成了 `if/else`。

### 又一个 `num_or` 咬人的地方（第三次）

`start_params()` 一开始用 `DataLoader.num_or(w, "nestScale", 1.0)` —— 而**塔防模式的

> 教训：`num_or()`（falsy 兜底）与 `num()`（缺失兜底）**语义不同**，

## 手感回归：移动模型（抓到一个 28% 的速度差）

第一刀就抓到了真问题：**Godot 侧把玩家的基础移动速度手抄成了 220，而真值是 172** ——
整整快了 28%。它之所以能藏这么久，是因为 `src/core/config.js` **根本没有进数据管线**：
导出脚本只导 `src/data/*`，于是 `PLAYER` / `VEHICLE` / `BEACON` 这些核心常量在 Godot 侧
全是手抄的，抄错也没人知道。

两处一起修：

1. **把 `src/core/config.js` 加进导出脚本**（`godot/data/config.json`，20 张表 83 条）——
   现在这些数字和其它数据一样走同一条管线，Godot 侧不许再手抄；
2. **完整移植 `updateMove`**（`player_move.gd`）：

| 项 | 规则（来自 config 的 PLAYER） |
|---|---|
| 基础速度 | **172** ×(1+speedMult) |
| 冲刺 | ×1.42（且**正在移动**且体力 > 1） |
| 击杀狂暴 | ×(1+killFrenzySpeed)（开拓者） |
| 负重惩罚 | 负载 > 90% 时 ×clamp(1-(load-0.9)×1.2, 0.55, 1) |
| 地形 | ×`speedAtPx` |
| 体力 | 冲刺 -17/s，否则 +21/s（再加科技 staminaRegen） |
| 闪避 | 560 速度 · 0.19 秒 · 冷却 0.85 · **无敌帧 0.28** · 消耗 22 体力 |

### 手感断言：逐帧轨迹

不只比常量，还比**逐帧轨迹**：五档场景（走路/冲刺/地形 0.7/超重/狂暴+加速）各跑 60 帧，
每 15 帧比一次位移与体力；闪避单独比「全程位移 = 560×0.19 = 106.4」。

实测各档速度：走路 **172** · 冲刺 **244.2** · 地形 0.7 → **120.4** · 超重 → **155.7** · 狂暴+加速 → **366.4**。

> 顺带又遇到 float32：闪避位移每帧经过 `Vector2` 累加，末几位必然和 JS 的 float64 不同，
> 这条用 `_approx32`（1e-6 容差）—— 和死区那条同源，注释里写清了原因。

**当前累计：Godot 断言 5708 条 + 长时模拟 9 条全绿；JS 版 622 条全绿。**
### 手感回归第二刀：射击几何（又抓到 6 处偏差）

把开火那段抽成 `gunplay.gd`（**玩家和防御塔共用**，不然两边会慢慢长歪），
对照 JS 的 `fireWeapon` 逐项修：

| 项 | Godot 原来的写法 | JS 的真值 |
|---|---|---|
| 默认散布 | `0.05` 弧度 | **`def.spread \|\| 0` → 默认 0**（原来白送 2.9° 误差） |
| 多弹道步长 | `(i/(n-1)-0.5)×0.18` | **`(b-(n-1)/2)×0.075`**（两管时原来宽了 2.4 倍） |
| 枪口距离 | `玩家半径+6 = 19px` | **18px** |
| 弹丸数 | 忽略 `def.pellets` | **霰弹枪一颗弹丸一条** |
| 穿透 | 只算科技 `pierce` | **`def.pierce + 科技`**（漏了武器自带穿透） |
| 弹丸半径 | 固定值 | **`subtype=='gun'` → 4，否则 6** |
| 寿命 | 默认值 | **`射程/速度 × 1.15`** |
| 随机源 | `randf_range`（不可复现） | **种子 RNG**（同种子同弹道，能上黄金对比） |

断言覆盖 9 种组合（3 把武器 × 0/1/2 条额外弹道）：弹道偏移序列、弹丸数、
弹药按弹道条数扣、枪口位置、半径、寿命、穿透、**奇数条时正中那条精确对准准星**、
偶数条时两侧对称；再用种子 RNG 打 200 发验证散布**始终落在 ±spread 内**。

> 又是 float32：枪口坐标与散布区间都经过 `Vector2`，末几位与 JS 的 float64 不同，
> 这两处用 `_approx32` 并注明原因。

**当前累计：Godot 断言 5851 条 + 长时模拟 9 条全绿；JS 版 622 条全绿。**
### 手感回归第三刀：相机（跟随公式 + 震屏 + 边界）

| 项 | Godot 原来 | JS 的真值 |
|---|---|---|
| 跟随 | `lerp(target, delta×8)` **线性** | **指数收敛 `t = 1-exp(-12·dt)`** |
| 震屏 | `bus_shake()` 是**空函数**（占位） | `shake(mag, time=0.32)` + 衰减 `k = 剩余时长 × 强度` |
| 边界 | 没有钳制（跑到地图边缘镜头会滑出去） | `_clamp()` 把视野锁在世界内 |
| 缩放 | 固定 1.0 | `1-exp(-6·dt)` 缓动 |

线性 `dt×8` 与指数 `1-exp(-12dt)` 的差别正是「手感发黏 / 跟不上」的来源：
前者在低帧率下明显落后、高帧率下又贴得太紧，后者与帧率无关。

**震屏现在是真会震了** —— 以前挨打、Boss 冲撞、基地被砸在 Godot 版里一点反馈都没有。
接法：`player.hurt` 信号（强度随伤害 2~12）与 `enemies.bus_shake()` 都指向 `CameraRig`。

断言：跟随 60 帧逐帧位置（并且断言**指数收敛确实比线性 dt×8 更快贴上目标**——
这条直接把「原来是错的」钉住了）、震屏衰减曲线与「偏移始终在 ±k 内」、
弱震动不覆盖强震动、边界钳制的 4 个越界/贴边用例、视野矩形。

**当前累计：Godot 断言 5888 条 + 长时模拟 9 条全绿；JS 版 622 条全绿。**
### 手感回归第四刀：换弹（花费 / 时机 / pending 语义）

| 项 | Godot 原来 | JS 的真值 |
|---|---|---|
| 花费 | **不要钱**（免费补满） | `ceil(需补 × 0.12 × ammoCostMult)` **金属** |
| 补弹条件 | `reloading` 归零就补满 | **只有 `beginReload()` 置过 `reloadPending` 才补** |
| 自动换弹 | `fire()` 里直接 `start_reload()`（不看钱） | 走 `autoReload()`：失败**只提示一次**，不刷屏 |
| 现场合成 | 没有 | 「弹药合成」实验：吃金属+硫磺**瞬间补满** |

`reloadPending` 这条是 JS 注释里专门写下的设计：

> 「空仓干等那 1.2 秒白送 30 发」的旧漏洞不会再出现 —— 没置位就算进度走完也只清进度、不给子弹。

手动设成 0.01 再 update，弹药必须还是 0）。

另外补了「弹药已满 → 拒绝」「金属不足 → 拒绝且不扣钱」「成功后清掉『已提示过』」
「打空后自动进入换弹」等 21 条断言。

**当前累计：Godot 断言 5909 条 + 长时模拟 9 条全绿；JS 版 622 条全绿。**

### 顺手修掉一条「会让测试随机变红」的断言

收尾跑验收时发现 JS 套件**偶尔**出现 `通过 332 · 失败 1`，但单独跑同一个套件十几次都全绿。

## 修掉「还没开始游戏就已经在打」—— 开场与二级界面重做

玩家反馈（原话）：

> 怎么我没开始游戏角色还没选后面就已经打上了，游戏开场的界面要做，二级界面都要做啊

### 根因

原来的「主菜单」只是**盖在一局正在运行的游戏上面**：`_ready()` 里先把世界生成、
敌人撒好、怪潮导演跑起来，最后才补一个菜单窗口。所以选角色的时候虫群已经在啃基地了。

### 改法

1. **前置流程走完之前，世界不生成、模拟不推进**：
   `_ready()` 只做前置准备（解析参数、读设置、取相机），开局逻辑全部搬进 `_start_run(params)`；
   `_process` 开头就是 `if not playing: return` —— 这一条就是那个 bug 的正解。
2. **`front_end.gd` 一整屏一屏的界面**（带不透明底，背后不会漏出战场）：
   **标题 → 模式 → 角色 → 星球与种子 → 生成中 → 落地**，另有设置屏。
3. **参数真的驱动开局**：模式（塔防 → `nestScale=0`、无角色、阵地半径 900）、
   角色（基础属性 + 被动数值进属性引擎）、星球（`planetIndex` 进世界生成）、种子。
4. **生成中有等待界面**：世界生成在 GDScript 里是阻塞的 4~5 秒，
   先画一屏「正在生成世界…（星球 N · 种子 …）」再开始算。
5. 游戏内 Esc 的暂停面板保持原样，两者互不干扰；`--menu=0` 仍然直进游戏（截图/联调用）。

界面截图：`tools/shots/front-0.png`（标题）、`front-1.png`（模式）、`front-2.png`（角色）、
`front-3.png`（星球）、`front-5.png`（设置）。

| 断言 | 为什么会随机红 | 修法 |
|---|---|---|
| `模拟性能足够（>2000 步/秒）` | 机器忙（同时跑 Electron 套件）时掉破阈值 | 改成**软检查**：只警告不判失败 |
| `没有巢时从屏幕外沿刷` | `spawnPoint` 会把点就近挪到空地（搜索半径 240px），随机方向下距离可能少一截（实测 823px） | 按 `standoff - 搜索半径` 判定，并在注释里写明这是**设计允许**的挪动 |

### ① 按键：原版是一张**可改键的表**，我却是手抄的

原版 `core/settings.js` 的 `DEFAULT_BINDS`：

| 动作 | 键 | 动作 | 键 |
|---|---|---|---|

| 冲刺 | Shift | **载具·虫巢·遗迹** | **F** |
| 采集·维修 | E | 换弹 | R |
| 切武器 | Q | 接管炮塔 | C |
| 治疗 | H | 拾取 | X |
| 标记 | Z | 快捷栏 | 1-8 |
| **建造** | **B** | **科技** | **T** |
| **城镇** | **G** | **实验科技** | **V** |
| **背包** | **Tab** | **地图** | **M** |
| 暂停 | Esc | 截图 | P |

我把键位手抄成了「1 铺基座 / 2 空投塔 / Tab 切页签」，**没有一个对得上**。

Godot 侧用 `Binds.apply_to_input_map()` 从表里建 InputMap，**不再手写 match**。
分发规则照抄原版 `main.js`：Esc 永远有效；面板开着只允许切面板；B 在放置模式里是取消；
F5 快存 / F9 快读 / F3 调试 / F4 流场。

新增 16 条断言把「键位表与 JS 原版一致」钉住（16/16 ✅）。

### ② 面板直达 + 建造模式

原版**每个面板一个键**（T/G/V/Tab/M），且打开面板会暂停；建造键 B 打开建造面板，
**选一座塔 → 进入放置模式 → 鼠标左键落位、右键或 B/Esc 取消**。
现在 Godot 侧同流程：面板里的按钮改成「建造 →」直接进放置模式，鼠标有预览、左键落位。

### ③ 虫巢入口：以前「在哪都能进」

原来按 F 直接找**最近的巢穴**就进副本，多远都行。现在 `_nearest_nest_entry(120px)`：
**必须站在巢口**（120px 内）才进得去，否则提示「附近没有可交互的东西」。
`F` 也按原版语义统一成「上下车 / 进虫巢 / 搜刮遗迹」三合一，按最近的来。

### ⑤ 走路一卡一卡：量化后是**每 0.35 秒一次 100ms 冻结**

写了 `tests/probe_hitch.gd` 边跑边量每帧耗时，结果很明确：

| 指标 | 修前 | 修后 |
|---|---|---|
| 每帧平均 | 4.82 ms | **0.28 ms** |
| p95 | 3.45 ms | 3.27 ms |
| **最慢一帧** | **107.92 ms** | **4.95 ms** |

两处原因，都修了：

1. **流场重算（90~110ms）在主线程**：新增 `AsyncFlow`（双缓冲 + 后台线程）——

2. **区块生成一帧做完一批**：新增 `FrameBudget`（一帧最多 1 个区块，按离玩家近的优先），
   并把 `Props` 里每候选地块都重新解析 JSON 的 `DataLoader.new().table()` 改成缓存。

### 流程断言（21 条）抓到一个**真 bug**

让他先研究「载具申请」很荒唐。现在 `pilot` **开局就带 `vehicle` 特性**：

- `createPlayer()` 里给（构造期就生效）**并且** `recomputeStats()` 里也给（重算后不会被抹掉）；
- Godot 侧在 `_build_stats()` 里按角色补 `vehicleUnlock`。

> 踩坑：只写在 `recomputeStats()` 里没用 —— 构造流程根本不调它，
> 结果「驾驶员开局没车」，直到第一次属性重算才出现（比如升了一级）。

### ③ 顺带修掉一个潜伏的 bug：构造时不重算属性

写这次验证时发现 `new RunState(...)` **不会**调用 `recomputeStats()` ——

## 规矩（沿用 JS 版的做法）

1. **不加运行时依赖**：只用 Godot 自带节点与 GDScript（Steam 走 GodotSteam 插件另说）。
2. **数据只在 `src/data/*.js` 里改**，然后重新导出；Godot 侧不手抄数值。
3. **每条断言都要能自动跑**（`node tools/godot-verify.mjs`），不靠「看起来对」。
4. 每次改完贴一张实机截图（`godot --path godot` 截图或 `godot-verify` 的对比图）。
